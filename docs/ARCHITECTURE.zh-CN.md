# WRobot - sdevil Enhanced 系统架构

中文 | [English](ARCHITECTURE.md)

## 设计原则

所有实时和安全关键的执行器决策都由 ESP32 负责。视觉、网页、手柄、语音和未来
的 LLM Agent 只提供高级意图，不能直接下发电机 PWM 或相电压。

## 组件职责

| 组件 | 职责 |
| --- | --- |
| ESP32-WROOM-32 | 平衡、FOC、偏航、腿控、动作、安全和命令仲裁 |
| MPU6050 | 机身姿态和角速度 |
| AS5600 x2 | 轮部位置和速度反馈 |
| 无刷电机 x2 | 通过 SimpleFOC 驱动车轮 |
| STS3032 x2 | 通过智能舵机总线控制腿部位置 |
| MaixCam | 视觉处理，并通过 UART 输出目标偏差 |
| Gamepad 手柄 | 蓝牙人工控制输入 |
| 网页控制器 | 通过热点或家庭 WiFi 控制；支持 WebSocket、wrobot.local 与 captive portal |

## 运行时数据流

```text
Gamepad通知 ------------------+
网页WebSocket/HTTP命令 -----+--> 命令仲裁 --> Wrobot目标值
MaixCam UART DX/DY --------+                     |
                                                v
MPU6050与AS5600反馈 --> LQR/偏航/腿控 --> 电机和舵机输出
```

网页方向命令有效期间会覆盖 Gamepad 摇杆轴，超过 500ms 未刷新或 WebSocket 断开即失效。延长后的回退窗口避免 HTTP 往返抖动反复清零按住中的命令；摇杆松手仍会立即发送零值。MaixCam
当前通过 `DX:x,DY:y;` 发送目标追踪偏差。

## 任务与核心分工

- Arduino `loop()` 负责传感器更新、平衡、偏航、腿部、动作组和 FOC 更新。
- HTTP、WebSocket、mDNS 与 captive DNS 服务运行在固定到 Core 0 的 FreeRTOS 任务中。
- 网页与主循环之间的共享状态使用 ESP32 临界区保护。
- 网络处理函数只更新高级命令状态，不直接调用电机驱动。

## 后续功能必须遵守的安全规则

1. 所有运动命令都必须有超时或明确的释放条件。
2. AI 和网络输入必须由 ESP32 校验并限制范围。
3. 停止、坐下、倒地恢复和物理断电具有更高优先级。
4. 网络解析和模型推理不能放进平衡主循环。
5. 新控制源必须接入命令仲裁层，不能直接修改 `motor.target`。
6. Web 动作和摄像头俯仰命令通过队列跨任务传递；网络回调不得直接调用运动核心。
7. 禁用轮毂电机时必须明确写入零相电压，不能保留上一次 PWM 占空比。
8. Gamepad 动作按钮使用上升沿触发，手柄断连时必须立即停止运动。

## 舵机校准策略

主控启动时不应自动执行会写入舵机零点/偏移量的校准。STS3032 的中位校准属于维护动作，它依赖机器人处在明确的机械基准位置；如果每次开机自动写入，可能把摔倒、半蹲、支架未放正或机构卡滞时的姿态误保存为新零点，导致零点越校越偏，也会增加持久化写入风险。

推荐策略是：开机只做只读健康检查，读取位置、负载、温度、电压等可用状态，并与预期待机姿态比较，用于提示舵机偏差、负载异常或机械磨损趋势。当前集成运动适配层没有实现可靠的写入式零点校准，因此 Web UI 不暴露无效按钮；以后实现并验证校准流程后，再从维护设置接入统一 `MotionCommand`。

## Motion Core 边界

运动控制现在隔离在 `MotionCommand` 和 `MotionCore` 后面：

```text
Web UI / WebSocket ----+
Gamepad 适配器 ------------+--> MotionCommand --> MotionCore --> integrated controller/devices/system
MaixCam UART ----------+
```

默认实现是 `MotionCoreAdapter`，它封装了当前仓库中维护的 `controller`、`devices` 和
`system/task` 代码。以后如果有新的运动核心版本，应新增或替换一个实现 `MotionCore` 的适配器，把稳定的 `MotionCommand` 合约映射到新核心内部 API。Web、WiFi、OTA、Camera、设置和 UI 代码不应直接 include 或调用运动控制内部实现。

导入运动代码中的内部 Gamepad 驱动没有继续使用。蓝牙、网页和摄像头输入都在核心外部统一转换成 `MotionCommand`，再由适配器写入 `host_data`。这样可以保持运动核心可替换，并避免 UART、蓝牙、WiFi 的所有权冲突。

## 固件体积策略

固件使用本地 `SimpleFOCMinimal` 库，只保留当前机器人实际需要的 FOC 部分：BLDC 电机控制、ESP32 3PWM 驱动、AS5600 I2C 传感器、PID 和低通滤波。不使用的 SimpleFOC 电流采样和其他硬件后端被排除，以降低构建时间和 Flash 压力。FastLED 也已替换为本地轻量 WS2812 状态灯驱动。

WS2812 状态灯必须通过 ESP32 RMT 驱动，不能回退到手写 GPIO bitbang。bitbang 实现在 WiFi/WebSocket 和运动任务同时运行时曾导致 ready 闪灯后的绿灯锁存常亮。修改 LED、OTA、Web 控制、摄像头预览或运动核心集成前，先阅读[工程经验记录](ENGINEERING_NOTES.zh-CN.md)。

## 柔和站立

当前集成运动核心使用基于反馈的起身过程来减少底盘位移。默认坐姿为缩腿向后支撑，重心位于轮轴后方。因此控制器先保持缩腿，让轮式平衡将轮轴移动到重心下方；俯仰角和俯仰角速度进入短暂就绪窗口后，再交给正常平衡控制，不使用固定的向前补偿。

轮式平衡输出在恢复窗口内逐渐接管。轮部里程计会保留为诊断数据，但起立阶段不会把它作为强闭环位置参考，因为轮胎打滑会让位移测量失真。恢复过程有时间上限，避免不稳定的起立持续后退。舵机反馈无效或尚未就绪时，使用保守回退值。

柔和站立不会使用固定的向前补偿。此类补偿受地面摩擦力、电池电压、载荷和机械磨损影响，可能增加摔倒风险。
