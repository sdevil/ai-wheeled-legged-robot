# 工程经验记录

本文记录 WRobot - sdevil Enhanced 调试过程中已经验证过的硬件经验。以后修改固件、Web UI、OTA、摄像头或运动核心时，应把这些内容当作回归保护规则。

## 状态灯

- RGB 状态灯是接在 `RGB_PIN 21` 上的 WS2812 类地址灯。
- 不要再用手写 GPIO bitbang 驱动 WS2812。这个实现在线上 WiFi、WebSocket、摄像头状态轮询和实时运动任务同时运行时不可靠，曾经出现固件状态已经是全黑，但某一颗绿灯仍然锁存常亮的问题。
- RGB 状态灯必须使用 ESP32 RMT 硬件外设发送。RMT 能提供稳定时序，可靠发送黑灯帧。
- 向 WS2812 链路发送多于实际灯珠数量的数据是安全的。当前固件发送 8 颗灯的数据，用来保证链路上的所有灯都能收到熄灭帧。
- 自检成功后，ready 指示灯应快速闪绿 6 次，然后熄灭。
- 低电量只在电量低于配置阈值时进入红色呼吸。
- GPIO13 是独立的绿色控制模式指示灯，不是 RGB ready 灯。Web/WiFi 模式应熄灭；Gamepad/Bluetooth 模式应常亮。
- LED 行为还在持续验证阶段，保留 `/api/diagnostics` 里的 `led` 字段，用于区分 GPIO13 和 RGB 链路状态。

## OTA 稳定性

- 最近几个版本的 OTA 已经稳定。当前稳定性依赖 OTA 期间暂停运动侧干扰，并使用现有 Web UI 上传流程。不要在 OTA 期间重新加入后台操作，除非同时在电池供电和 USB 供电下测试通过。
- OTA 只能在维护模式下执行。
- OTA 期间必须禁用运动和动作控制。
- OTA 最低电量阈值是 30%，除非用户明确确认外部稳定供电。
- ESP32 使用双 OTA 应用分区并支持回滚。新固件启动成功后必须确认 OTA 镜像有效，否则会影响回滚逻辑。
- Web UI 上传进度应显示本地 XHR 上传进度；上传过程中不要显示固件侧的旧状态文本，例如 `Idle`。

## Web 控制

- Web 和 Gamepad 控制都必须进入同一条 `MotionCommand` 路径。两者体感不同通常说明输入映射或传输层有 bug。
- 控制优先使用 WebSocket，但 HTTP fallback 必须也能发送非零移动命令。之前出现过 fallback 只发送停止命令，导致 WebSocket 失败时 Web UI 控制完全无反应的问题。
- 状态轮询或视频刷新不应在用户按住摇杆时重置运动命令。

## 摄像头预览

- 移动浏览器里的 MJPEG 流可能出现黑屏，即使摄像头服务器仍然在线。Web UI 应在加载失败、画面长时间无效、页面重新获得焦点或回到前台时自动重连视频流。
- 没有视频时显示明确的 `No Video Signal`，不要显示裂图。
- 摄像头固件和主板固件版本号相互独立。

## 运动核心

- `MotionCommand` 是稳定边界。Web UI、Gamepad、Camera、UART、OTA 和设置代码不应直接调用 integrated motion controller 内部实现。
- 实时传感器、控制和电机任务应保持在运动核心上，避免 WiFi/Web 工作负载打断电机输出。
- 修改站立/坐下逻辑时，必须保持平滑过渡，避免使用依赖地面摩擦、电池电压、负载和机械磨损的固定补偿。
- 坐下动作必须先在平衡状态下缓慢下蹲，然后再轻柔收腿。不要加入可能让机器人向前栽头的轮子推力。
